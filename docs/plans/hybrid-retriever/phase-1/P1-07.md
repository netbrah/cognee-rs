# P1-07 — Hybrid module — chunk + BM25 lane

## Goal

Port the Python `cognee/modules/retrieval/hybrid/{results,pairs,ranking,chunks}.py` files
into a new `crates/search/src/retrievers/hybrid/` module, giving the future `HybridRetriever`
(Phase 1, `SearchType::HybridCompletion`) its chunk-ranking core: a per-query Okapi BM25
lexical lane merged with the existing vector `DocumentChunk_text` / `TextSummary_text`
channels via Reciprocal Rank Fusion (RRF), with optional importance-weight boosting. This
task delivers the pure ranking/merge logic and its vector-orchestration wrapper only — it
does **not** wire a `SearchRetriever` impl, `SearchType` variant, or wire-level params (those
land in a later task).

## Prerequisites

- **P1-02** — adds a batched retrieve-by-ids capability to `VectorDB` (mirrors Python's
  `vector_engine.retrieve(collection_name, ids)`). Assumed shape used below:
  `async fn retrieve(&self, data_type: &str, field_name: &str, ids: &[Uuid]) -> VectorDBResult<Vec<SearchResult>>`.
  If P1-02 lands with a different name/signature, update the call sites in `chunks.rs`
  accordingly — the behavior needed is "fetch by id, missing ids silently omitted from the
  result, no error" (matches `vector_engine.retrieve` semantics used at
  `hybrid/chunks.py:184` and `hybrid/chunks.py:239-242`).
- **P1-03** — the BM25 lexical lane (`BM25ChunksRetriever` port): Okapi BM25 `k1=1.5 b=0.75`,
  `idf = ln(1 + (N-df+0.5)/(df+0.5))`, summed over unique query terms, tokenized with
  `DEFAULT_STOP_WORDS` (`/tmp/cognee-python/cognee/modules/retrieval/utils/stop_words.py`).
  Assumed shape: a constructor taking `top_k`/`with_scores` that rebuilds its corpus from the
  graph on every call (no process-lifetime cache — see Parity notes) and returns
  `Vec<(serde_json::Value, f32)>` scored chunk payloads.
- **P1-05** — adds `importance_weight: Option<f64>` (default `0.5`, Python-faithful) to the
  `DocumentChunk` model (`crates/models/src/document_chunk.rs`) so it is present in the
  vector-point metadata read by `ranking.rs`. At the time of writing,
  `crates/models/src/document_chunk.rs` has no `importance_weight` field (confirmed by
  reading the file) — this task's `ranking.rs` reads the field defensively (missing/non-numeric
  → `0.5`) so it still compiles and behaves correctly even if P1-05 has not landed yet, but
  the importance-weight boost will be a no-op (`0.5` for everything) until it does.

Assumed state: `crates/search` compiles against `cognee-vector`, `cognee-models`, and
`cognee-graph` as of commit `82310dc` (current `main`). No `hybrid` module exists yet under
`crates/search/src/retrievers/` (verified: `find crates/search -iname '*hybrid*'` returns
nothing).

## Implementation steps

1. **Scaffold the module.** Create `crates/search/src/retrievers/hybrid/mod.rs` with
   `mod results; mod pairs; mod ranking; mod chunks;` and re-export the public surface this
   task defines (`pub(crate) use chunks::{retrieve_hybrid_chunks, HybridChunksResult};`). Add
   `mod hybrid;` to `crates/search/src/retrievers/mod.rs` (keep it private/`pub(crate)` — no
   `SearchRetriever` impl lives here yet, so nothing needs crate-external visibility).

2. **`results.rs` — port `hybrid/results.py` (60 lines) onto `SearchItem`.** Rust already has
   a normalized result shape at `crates/search/src/types/search_result.rs:9-13`
   (`SearchItem { id: Option<Uuid>, score: Option<f32>, payload: Value }`) and a converter
   `search_results_to_context` (`crates/search/src/retrievers/context_items.rs:5-19`) that
   turns `cognee_vector::SearchResult` into `Vec<SearchItem>`. Since every lane in this task
   (BM25, vector, summary) can be normalized to `SearchItem` at its call site, Python's
   duck-typed `Any` collapses to `&SearchItem` — port the six functions as:
   - `payload(item: &SearchItem) -> &serde_json::Value` — return `&item.payload` (Python
     `results.py:5-9` defensively falls back to `{}` for non-dict input; Rust's `SearchItem`
     always carries a `Value`, so add a small `as_object_or_empty` helper only where callers
     need to iterate keys, e.g. `belongs_to_set` lookup).
   - `display_value(value: &Value) -> Option<String>` — mirror `results.py:12-18`: `Null` →
     `None`; `String`/`Number`/`Bool` → trimmed string, empty → `None`; `Array`/`Object` →
     `None`. (Python also accepts a bare `UUID` object; Rust ids are always JSON strings by
     the time they reach `payload`, so that branch is unreachable and can be omitted.)
   - `result_id(item: &SearchItem) -> Option<String>` — `display_value(payload(item).get("id"))`
     or fall back to `item.id.map(|u| u.to_string())`, matching `results.py:21-23`.
   - `scored_payload((payload, score): (Value, f32)) -> (Value, f32)` — Rust's BM25 lane
     (P1-03) is statically typed, so the dynamic-shape guard from `results.py:26-32` is
     vestigial; keep the function only to clamp a `NaN`/negative score to `0.0` for defensive
     parity, called from `search_bm25_chunks`.
   - `payload_matches_node_filter(payload: &Value, node_name: Option<&[String]>, operator: &str) -> bool`
     — port `results.py:35-51`. **Divergence from Python:** Rust's `belongs_to_set` entries are
     JSON values built at `crates/models/src/document.rs:148-178` as
     `{"id":..,"name":..,"type":"NodeSet"}` objects (not the plain dataset-id strings Python
     stores), except the dataset-membership form emitted by `DataPoint::new` /
     `document_chunk.rs`, which is still a bare string
     (`crates/models/src/data_point.rs` — `belongs_to_set: dataset_id.map(|id| vec![json!(id.to_string())])`).
     So the entry-to-name step must be: if the entry is a JSON string, use it as-is; if it is
     an object, read `.name` as a string and skip the entry if absent/non-string; otherwise
     skip. Build the resulting `HashSet<String>` and apply `AND` (`issubset`) vs `OR`
     (non-empty intersection) exactly as Python (only the literal string `"AND"` selects
     AND semantics; anything else, including unrecognized values, behaves as `OR` — no
     validation/error path, matching `results.py:49-51`).
   - `first_display_value(values: &[&Value]) -> Option<String>` — port `results.py:54-59`.

     — two-phase loop exactly as `pairs.py:15-65`: first iterate `(bm25_rank, bm25_chunks)`
     then `(vector_rank, vector_chunks)`, calling `_find_chunk_summary_pair` /
     `_new_chunk_summary_pair`, applying the "first-rank-wins" rule (`pair[rank_field]` set

   - `source_chunk_ids_to_load(pairs: &[ChunkSummaryPair]) -> Vec<String>` — port

4. **`ranking.rs` — port `hybrid/ranking.py` (59 lines), Phase 1 subset only.** Signature:
   `rank_chunk_summary_pairs(pairs: Vec<ChunkSummaryPair>, limit: usize, use_importance_weight: bool) -> Vec<ChunkSummaryPair>`
   (the Python function also threads `use_truth_weight`/`q_coords`/`truth_state_by_id`/
   `current_truth_epoch` for the Phase-2 truth-subspace boost — per the locked Phase-2
   deferral, do **not** implement or accept those parameters here; Phase 2's task will extend
   this signature, gated by a default-off flag, without touching the Phase-1 code path).
   - `rrf_k(chunks_top_k: usize) -> usize { (20 + 2 * chunks_top_k).clamp(30, 60) }` — port
     `_rrf_k` (`ranking.py:51-52`); note the Python `max(30, min(60, ...))` and Rust
     `.clamp(30, 60)` are equivalent for non-negative inputs.
   - `importance_factor(chunk_payload: &Value) -> f64` — port `_importance_factor`
     (`ranking.py:55-59`): `chunk_payload.get("importance_weight").and_then(Value::as_f64)`,
     default `0.5` if missing or not a JSON number (this also naturally rejects
     strings/bools/arrays, matching Python's `isinstance(x, (int, float))` guard — note
     Python's `isinstance(True, int)` is `True` in CPython, so a literal `bool` payload value
     *would* pass Python's guard; this is an intentional, documented divergence since it is
     not a realistic payload shape). Clamp to `[0.0, 1.0]`, return `0.75 + 0.5 * importance`.
   - `rank_chunk_summary_pairs`: if `limit == 0` return `vec![]`. Compute `k = rrf_k(limit)`.
     For each pair with `chunk.is_some()`: collect present ranks from
     `(bm25_rank, vector_rank, summary_rank)` in that order, skip the pair if none are set
     (`ranking.py:26-32`); `rrf_score: f64 = ranks.iter().map(|r| 1.0 / (k + r + 1) as f64).sum()`;
     `final_score = rrf_score * if use_importance_weight { importance_factor(payload) } else { 1.0 }`;
     `chunk_id_string = pair.chunk_id.clone().or_else(|| result_id(chunk)).unwrap_or_default()`.
     Collect `(final_score, rrf_score, min_rank, chunk_id_string, pair)` tuples, sort with a
     comparator equivalent to Python's `key=lambda item: (-final_score, -rrf_score, min_ranks, chunk_id)`
     — i.e. descending `final_score` (use `f64::total_cmp` per the locked decision, so `NaN`/
     `-0.0` sort deterministically), then descending `rrf_score`, then ascending `min_rank`,
     then ascending `chunk_id_string` (`Ord` on `String`) — then truncate to `limit`.

## Parity notes

- **BM25 constants** (owned by P1-03, consumed here): `k1 = 1.5`, `b = 0.75`,
  `idf(token) = ln(1 + (N - df + 0.5) / (df + 0.5))`, score summed over **unique** query
  terms only (`bm25_retriever.py:74-105`). This task does not reimplement BM25; it only
  filters/shapes its output.
- **RRF**: `rrf_k = clamp(20 + 2*chunks_top_k, 30, 60)` (`ranking.py:51-52`); `rrf_score =
  Σ 1/(rrf_k + rank + 1)` over the 0-based ranks present for a chunk in `{bm25, vector,
  summary}` (`ranking.py:34`, `pairs.py:24-42,44-63` for where ranks are assigned).
- **Importance factor**: `0.75 + 0.5 * clamp(importance_weight, 0, 1)`, default `0.5` when
  the payload's `importance_weight` is missing or non-numeric (`ranking.py:55-59`).
- **Sort key**: `(-final_score, -rrf_score, min(ranks), chunk_id_string)` ascending, i.e.
  final_score desc → rrf_score desc → min-rank asc → chunk_id string asc
  (`ranking.py:47`). Use `f64::total_cmp` for the two float comparisons (workspace convention
  for total ordering over floats containing possible `NaN`/`-0.0`).
- **`summary_id_for_chunk` id scheme**: `uuid5(chunk_uuid, "TextSummary")` —
  `pairs.py:91-96` — already implemented identically in
  `crates/cognify/src/summarization/models.rs:65` as `Uuid::new_v5(&chunk_id, b"TextSummary")`.
  `pairs.rs` must compute the exact same two-liner locally (no cross-crate call — see step 3)
  so the two never drift.
- **`belongs_to_set` shape divergence** (Rust vs Python): Python stores plain dataset-id
  strings; Rust's `classify_documents` (`crates/models/src/document.rs:148-178`) stores
  `NodeSet` **objects** `{"id", "name", "type": "NodeSet"}` for document-level node sets,
  while `DataPoint::new`'s dataset-membership entries remain plain strings
  (`crates/models/src/data_point.rs`). `payload_matches_node_filter` must read `.name` off
  object entries and tolerate bare-string entries — this is called out explicitly in the
  brief and is **not** a bug to fix, just a shape this port must handle.
  `node_name_filter_operator`: only the literal `"AND"` selects AND semantics; anything else
  (including case variants or garbage) is OR — no validation error, matching Python exactly
  (unlike the stricter `AND`/`OR`-only validation in
  `crates/search/src/graph_retrieval/brute_force_triplet_search.rs:126-130`, which this port
  intentionally does **not** copy).
- **`NoDataError` → `SearchError::NotFound`**: Python raises a dedicated
  `cognee.modules.retrieval.exceptions.exceptions.NoDataError` when the required
  `DocumentChunk_text` collection is missing (`chunks.py:170-173`). Rust's
  `crates/search/src/types/errors.rs` has no equivalent variant; this task reuses
  `SearchError::NotFound`, matching the existing convention in `ChunksRetriever` and
  `SummariesRetriever`. If a later task wants byte-for-byte error-type parity with the Python
  SDK's exception hierarchy, that is a separate, explicit decision — not silently introduced
  here.
- **Node-name filter push-down divergence**: Python's `vector_engine.search(..., node_name=...,
  node_name_filter_operator=...)` filters server-side inside the vector adapter. Rust's
  `VectorDB::search_similar` (`crates/vector/src/vector_db_trait.rs:67-73`) has no such
  parameter, so this port filters client-side after over-fetching
  (`fetch_limit = (limit*4).max(limit+20)` when `node_name` is set). **This is a known,
  accepted approximation**: if fewer than `limit` matching results exist within the
  over-fetched candidate window even though more exist in the full collection, Rust will
  return fewer/different candidates than Python for the same query — acceptable under the
  ~50% structural-parity tolerance, but worth revisiting if cross-SDK parity tests show
  systematic under-filling on node-scoped hybrid queries.
- **BM25 lane never hard-fails the search**: a BM25 lane error is logged and treated as an
  empty channel (`chunks.py:124-128`); only the *required* `DocumentChunk_text` vector lane
  can turn a missing collection into a hard error.
- **Truth-subspace (Phase 2) params are intentionally absent** from `ranking.rs`'s and
  `chunks.rs`'s Phase-1 signatures — see step 4/5. Do not add unused parameters "for future
  use" in this task; Phase 2's task will extend the signatures when it lands.

## Risks & open items

- **P1-02/P1-03/P1-05 interface drift**: this doc assumes reasonable signatures for the
  retrieve-by-ids `VectorDB` method, the BM25 retriever constructor/output shape, and the
  `importance_weight` field location, none of which exist in `main` yet (all three sibling
  docs were empty directories at the time this was written — confirmed via `find`). Update
  the call sites in `chunks.rs`/`ranking.rs` if the landed interfaces differ from what is
  assumed here.
- **Over-fetch multiplier is a guess** (`(limit*4).max(limit+20)`) with no existing
  precedent in the codebase and no tuning data yet; revisit once cross-SDK parity runs
  surface real under/over-fetch behavior on node-scoped queries.
- **`SearchError::NotFound` vs a dedicated `NoData` variant**: reusing `NotFound` matches
  existing convention but is a deliberate, low-risk divergence from Python's distinct
  exception type — flag if a later task wants richer error taxonomy on the wire.
- **`hybrid` module is `pub(crate)`-only for now**: no `SearchType::HybridCompletion`, no
  `SearchRetriever` impl, no `SearchParams` knobs are added by this task (those are locked
  for a later task per the wire-exposure decision). This task is inert from the outside —
  acceptance here is purely "the module compiles, is unit-tested, and is ready to be called."
- **Concurrency primitive choice**: `tokio::try_join!` requires the `"macros"` feature on the
  library target (not just dev-dependencies); confirm this doesn't pull in an unwanted
  `#[tokio::main]`-style proc-macro surface for a library crate — it does not (the macro
  feature also gates `join!`/`try_join!`/`select!`, which are the only ones used here).
