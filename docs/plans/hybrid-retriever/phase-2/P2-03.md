# P2-03 — Truth-subspace: vector persistence

## Goal

Give the truth-subspace centroid math a durable home in the vector layer: a
generic `upsert_raw_vectors` escape hatch on `VectorDB` for small,
system-owned vector state that must never be re-embedded, plus the two I/O
functions (`load_centroids`, `upsert_centroids`) that use it to read and write
per-dataset truth centroids. This is pure plumbing — no retriever wires it up
yet (that is Phase-2 execution, deferred per the locked decisions) — but it
must round-trip centroid payloads byte-for-byte so that when execution lands,
truth-subspace reranking is deterministic and reproducible across restarts.

## Implementation steps

1. **Trait method.** In `crates/vector/src/vector_db_trait.rs`, add:
   ```rust
   async fn upsert_raw_vectors(
       &self,
       data_type: &str,
       field_name: &str,
       points: &[VectorPoint],
   ) -> VectorDBResult<()> {
       let _ = (data_type, field_name, points);
       Err(VectorDBError::StorageError(
           "upsert_raw_vectors is not implemented for this adapter".to_string(),
       ))
   }
   ```
   Place it near `index_points` (after `delete_points` is a reasonable
   location, following the existing default-impl style used for
   `delete_points`/`list_collections`/`prune`/`batch_search_similar`). Document
   on the method that this is for small, system-owned vector state (centroids,
   not content) where the caller has already computed the vector and
   re-embedding from text would be wrong — mirroring the Python docstring at
   `vector_db_interface.py:66-79`.

   Each point is a full `VectorPoint { id, vector, metadata }` — reuse the
   existing type rather than inventing a `{id, vector, payload}` struct; the
   Python `points: list[dict]` with `id`/`vector`/`payload` keys
   (`centroids.py:186-190`) maps directly onto `VectorPoint`'s
   `id`/`vector`/`metadata` fields. There is no Rust equivalent of Python's
   `payload_schema: Optional[Any]` parameter — Rust has no adapter-level
   runtime schema validation hook, and validation instead happens where the
   caller deserializes `TruthCentroidPayload` from the retrieved metadata (see
   Parity notes). Drop the parameter from the Rust signature.

2. **`MockVectorDB::upsert_raw_vectors`.** Implement as an unconditional
   insert-or-replace by id into the `(data_type, field_name)` collection
   (create the collection lazily with the incoming vector's dimension if it
   does not exist yet — Python's adapters likewise do not require
   `create_collection` to have been called first for this path since the
   caller may be seeding a brand-new `TruthCentroid_vector` collection).
   **Do not** call the dataset-membership merge helper used by
   `index_points` (`VectorPoint::merge_dataset_membership`) — centroid points
   are not content-addressed across datasets, each `centroid_id(dataset_id,
   slot)` already scopes one dataset, so union-of-membership semantics do not
   apply. A plain full-metadata replace is correct and matches Python's
   `create_data_points`-free direct write in `upsert_centroids`.

3. **`BruteForceVectorDB::upsert_raw_vectors`.** Same semantics as step 2:
   lazily create the collection (reuse the existing `Self::key(data_type,
   field_name)` helper), replace any existing point with the same id in the
   `Vec<VectorPoint>` (or append if absent), skip the
   `merge_dataset_membership` call that `index_points` performs.

4. **`LanceDbAdapter::upsert_raw_vectors`.** Reuse the existing
   `collection_name(data_type, field_name)` helper and the same Arrow
   `RecordBatch` construction path `index_points` uses (id / vector / metadata
   columns), but skip whatever dataset-membership-union step `index_points`
   performs before writing, and open-or-create the table if it does not exist
   yet (mirrors `index_points`'s existing "create table on first write"
   behavior for a new `(data_type, field_name)` — reuse it if `index_points`
   already lazily creates; otherwise call `create_collection` first with the
   incoming vector's dimension).

5. **`PgVectorAdapter::upsert_raw_vectors`.** Reuse
   `Self::collection_name(data_type, field_name)` and the same
   `INSERT ... ON CONFLICT (id) DO UPDATE SET vector = EXCLUDED.vector,
   metadata = EXCLUDED.metadata` batched-insert pattern `index_points` uses
   (`pgvector_adapter.rs` around the `BATCH_SIZE`-chunked loop), but do
   **not** call `fetch_metadata`/`merge_dataset_membership` first — write the
   incoming metadata verbatim. Create the table via `create_collection` if
   `has_collection` returns false (the `TruthCentroid_vector` collection will
   not exist on first write since nothing else creates it).

6. **`load_centroids`** in `crates/truth-subspace/src/centroids.rs` (parity
   target: `centroids.py:165-176`):
   ```rust
   pub async fn load_centroids(
       vector: &dyn VectorDB,
       dataset_id: &str,
       k: usize,
   ) -> VectorDBResult<Vec<TruthCentroidPayload>> {
       let ids: Vec<Uuid> = (0..k).map(|slot| centroid_id(dataset_id, slot as i64)).collect();
       let rows = vector
           .retrieve_points("TruthCentroid", "vector", &ids)
           .await?;
       let mut centroids: Vec<TruthCentroidPayload> = rows
           .into_iter()
           .filter_map(|row| serde_json::from_value(json_from_metadata(&row.metadata)).ok())
           .filter(|c: &TruthCentroidPayload| c.dataset_id == dataset_id)
           .collect();
       centroids.sort_by_key(|c| c.slot);
       Ok(centroids)
   }
   ```
   Use `data_type = "TruthCentroid"`, `field_name = "vector"` so the derived
   collection name (`"{data_type}_{field_name}"`, the shared convention across
   `MockVectorDB::collection_key`, `BruteForceVectorDB::key`,
   `lancedb_adapter::collection_name`, `PgVectorAdapter::collection_name`)
   is exactly `TruthCentroid_vector`, matching Python's
   `TRUTH_CENTROID_COLLECTION` constant literally. Deserialize each
   `VectorPoint.metadata` map as `TruthCentroidPayload` (build a
   `serde_json::Value::Object` from the `HashMap<String, Value>` first);
   silently skip rows that fail to parse (mirrors Python's `if not
   isinstance(payload, dict): continue` guard at `centroids.py:171-172` — the
   Rust equivalent failure mode is a deserialize error, treated the same way).
   Keep the defensive `dataset_id` equality filter even though `centroid_id`
   already scopes the id to one dataset — it guards against a hash collision
   or stale/corrupted payload, exactly as Python does at `centroids.py:174`.

7. **`upsert_centroids`** (parity target: `centroids.py:179-194`):
   ```rust
   pub async fn upsert_centroids(
       vector: &dyn VectorDB,
       centroids: &[TruthCentroidPayload],
   ) -> VectorDBResult<()> {
       if centroids.is_empty() {
           return Ok(());
       }
       let points: Vec<VectorPoint> = centroids
           .iter()
           .map(|c| {
               let id = centroid_id(&c.dataset_id, c.slot);
               let vector = c.centroid.iter().map(|v| *v as f32).collect();
               let metadata = metadata_from_payload(c); // serde_json::to_value(c) as HashMap
               VectorPoint { id, vector, metadata }
           })
           .collect();
       vector
           .upsert_raw_vectors("TruthCentroid", "vector", &points)
           .await
   }
   ```
   Note the `f64` → `f32` narrowing: `TruthCentroidPayload.centroid` is
   `Vec<f64>` (Python `list[float]`) but `VectorPoint.vector` is `Vec<f32>` —
   cast on the way in/out and document the precision loss (see Parity notes).

8. Add both functions to `crates/truth-subspace/src/lib.rs`'s public surface
   next to whatever P2-02 already re-exports (`centroid_id`, `normalize`,
   `weighted_centroid`, etc.).

9. Run `cargo fmt`, `cargo check --all-targets`, `cargo clippy --all-targets`,
   then `cargo test -p cognee-vector -p cognee-truth-subspace`, then
   `scripts/check_all.sh`.

## Parity notes

- **Collection name**: `TruthCentroid_vector` must be produced by Rust's
  `"{data_type}_{field_name}"` convention with `data_type = "TruthCentroid"`,
  `field_name = "vector"` — an exact string match to Python's
  `TRUTH_CENTROID_COLLECTION` (`constants.py:1`), so a future cross-SDK
  read/write test on this collection is possible even though it is out of
  scope for this task.
- **Centroid id formula**: `uuid5(NAMESPACE_OID, f"TruthCentroid:{dataset_id}:{slot}")`
  (`centroids.py:20-21`) → Rust `Uuid::new_v5(&NAMESPACE_OID,
  format!("TruthCentroid:{dataset_id}:{slot}").as_bytes())` — this is P2-02's
  `centroid_id` fn, reused as-is here; confirm `dataset_id` is formatted with
  `.to_string()` on a `Uuid` (or passed through as `&str` if the caller already
  has a string) so the seed bytes are byte-identical to Python's
  `str(dataset_id)` interpolation.
- **`load_centroids` slot range**: build ids for `slot in 0..k` (`k` defaults
  to `DEFAULT_K = 8`), not "however many centroids exist" — a dataset with
  fewer than `k` centroids simply gets fewer non-`None` `retrieve_points`
  hits, which the Rust retrieve-by-id method should already handle by
  omitting misses from its result `Vec` (matching Python's `rows` list, which
  is however many of the `k` ids resolved).
- **Sort by slot**: `sorted(centroids, key=lambda centroid:
  centroid.slot)` (`centroids.py:176`) → Rust `.sort_by_key(|c| c.slot)`.
  Slot is not guaranteed to come back in order from the vector store since
  ids are looked up individually, not range-scanned.
- **Dataset-id defensive filter**: Python re-checks `centroid.dataset_id ==
  str(dataset_id)` after `model_validate` (`centroids.py:172-174`) even
  though the id already encodes the dataset — preserve this exactly, do not
  optimize it away.
- **`upsert_centroids` empty guard**: `if not centroids: return` (
  `centroids.py:180-181`) → Rust must return `Ok(())` immediately for an
  empty slice without calling `upsert_raw_vectors` at all (avoids a
  needless empty-batch round trip, and avoids adapters that assert
  non-empty `points`).
- **Payload symmetry**: Python's `points` payload is
  `centroid.model_dump()` — the *entire* `TruthCentroidPayload`, including
  the `centroid` vector itself, duplicated inside the JSON payload alongside
  the raw vector column (`centroids.py:184-190`). Rust must do the same: the
  `VectorPoint.metadata` JSON blob for a centroid point contains the full
  `TruthCentroidPayload` (including its own `centroid: Vec<f64>` field),
  which is redundant with `VectorPoint.vector` but intentional — Python keeps
  it so a plain `retrieve()` without a paired ANN query still yields a
  self-describing row.
- **`f64` vs `f32` divergence (Rust-only, intentional)**: Python vectors are
  untyped `list[float]` (i.e. `f64`-precision in effect); Rust's `VectorPoint.
  vector` is `Vec<f32>` throughout the vector crate (see
  `crates/vector/src/models.rs:12`). `upsert_centroids` narrows `f64 → f32`
  when building the `VectorPoint`, and `load_centroids` reconstructs
  `TruthCentroidPayload.centroid: Vec<f64>` from the deserialized JSON
  payload (not from the narrowed `VectorPoint.vector`), so the *payload*
  round-trips at full `f64` precision even though the ANN-searchable vector
  column is `f32`. Document this as an accepted precision divergence — it
  does not affect structural parity (slot assignment, cosine nearest-slot
  choice) at the tolerances this project already accepts for cognify
  (locked decision #2).
- **No dataset-membership union**: unlike `index_points`
  (`VectorPoint::merge_dataset_membership`, `crates/vector/src/models.rs:71-94`),
  `upsert_raw_vectors` must **not** merge `dataset_ids`/`dataset_id` metadata
  from a previous point at the same id. Python's `upsert_centroids` has no
  such concept at all (`vector_engine.upsert_raw_vectors` is a raw write);
  introducing a merge step here would be a Rust-only bug, not a port of
  anything in Python.
- **`payload_schema` is inert in Rust**: Python threads
  `payload_schema: Optional[Any] = None` through to `upsert_raw_vectors` and
  passes `TruthCentroidPayload` as that argument (`centroids.py:192`) — some
  Python adapters use it for provider-side schema declaration. No Rust
  adapter needs this (schema is enforced by `serde` deserialization at the
  `load_centroids` call site), so the parameter is dropped entirely rather
  than threaded through and ignored. Document this as an accepted API
  divergence in the trait doc-comment.

## Risks & open items

- **P1-02 method name/signature is assumed**, not verified against a landed
  file (phase-1 task docs did not exist on disk at the time this doc was
  written). If P1-02 lands with a different name, arity, or error-handling
  contract for retrieve-by-id, update step 6 and the `load_centroids` body
  accordingly before merging this task.
- **P2-02 crate layout is assumed** (`crates/truth-subspace/`, module names,
  `TruthCentroidPayload` field types) for the same reason. If P2-02 lands
  with different module boundaries, this task's file list needs a pass.
- **LanceDB table creation from `upsert_raw_vectors` on a brand-new
  collection**: confirm whether `index_points` already lazily creates a
  table when the collection does not exist, or requires a prior
  `create_collection` call. If the latter, `upsert_raw_vectors` must call
  `create_collection(data_type, field_name, dimension)` itself the first
  time (since nothing else creates `TruthCentroid_vector` ahead of time) —
  confirm this against the current `lancedb_adapter.rs::create_collection`/
  `index_points` behavior when implementing, not just from this spec.
  Same question applies to `PgVectorAdapter`.
- **`f64`→`f32` precision narrowing** on the vector column is an accepted,
  documented divergence (see Parity notes) but has not been validated against
  the actual nearest-slot cosine assignment at Phase-2 execution time; if a
  future structural-parity run shows slot misassignment near a tie, this is
  the first place to look.
- **No dataset scoping at the collection level**: all datasets' centroids
  live in one shared `TruthCentroid_vector` collection, disambiguated only by
  the `dataset_id`-scoped id and the defensive payload filter. This matches
  Python exactly, but means a `list_collections()`/`prune()` call touches
  every dataset's centroids at once — acceptable for now, flagged here in
  case a future multi-tenant isolation requirement wants per-dataset
  collections instead.
- **No migration for pre-existing installs**: since no prior Rust code
  writes to `TruthCentroid_vector`, there is nothing to backfill — this is
  the "existing datasets: documented degradation, no backfill" locked
  decision applied trivially (there is no old data to degrade).
